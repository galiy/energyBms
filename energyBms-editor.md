# energyBms-editor — архитектура приложения

Документ фиксирует результаты анализа для разработки кросс-платформенного
**GUI-приложения** для просмотра телеметрии/параметров BMS Enjie EMU110x и
**изменения/сохранения параметров** через RS485 (COM или прозрачный TCP-шлюз)
или BLE. Опирается на факты из `protocol-BLE.md`, `protocol-485.md`,
`DEVICE_SNAPSHOT.md`, `README.md`.

## 1. Цель и рамки

- Читать телеметрию (`0x42`), состояние/защиты (`0x44`), инфо (`0x4F/0x51`),
  параметры (`0x47`), время (`0x4D`), SN (`0xA4`).
- Изменять и сохранять **параметры** (`0xA1`, весь блок 169 Б) — по явному
  разрешению пользователя. Прочие записи (время `0x4E`, CAN-протокол `0x63`/
  `0xA6`, SN, история) в текущей версии **не реализованы**.
- Один и тот же UI на **Windows 64** и **Linux 64**, нативное GUI (не web-ui).
- Каналы связи: **BLE** (BT2-мост), **RS485** через COM-порт или через
  **прозрачный TCP-шлюз**.
- Экономия токенов при разработке: минимум бойлерплейта, максимум переиспользования
  словаря параметров и логики на всех каналах.

## 2. Выбранный инструмент: Python + PySide6

**Решение: Python + PySide6 (Qt6).**

| Слой | Библиотека | Назначение |
|------|-----------|-----------|
| GUI | **PySide6** (Qt6) | Нативное окно, таблицы, диалоги, редакторы параметров |
| Графики | `pyqtgraph` (или `QtCharts`) | Realtime-графики телеметрии |
| COM / RS485 | `pyserial` | COM (Win) и `/dev/tty*` (Linux); `socket://host:port` для TCP-шлюза |
| TCP-шлюз | `socket` / `serial.serial_for_url` | Прозрачный мост байт TCP ↔ RS485 |
| BLE | `bleak` | Единый асинхронный BLE API (Win10+/BlueZ Linux) |
| Конфиг | `json` рядом с запускаемым модулем | Последние применённые настройки соединения (`energybms_editor.json`) |

> **Реализация.** Настройки хранятся в `energybms_editor.json` рядом с
> запускаемым модулем (портативно), а не в `.kilo/` (в `gitignore` файл всё
> равно закрыт). Графики (`pyqtgraph`) в текущей версии не используются.

Обоснование выбора:

- **Экономия токенов:** Python/PySide6/`bleak`/`pyserial` хорошо известны LLM,
  минимум кода на кадры/CRC/UI.
- Парсеры протокола — чистые функции без GUI, легко тестируются и рефакторятся.
- Нативно на обеих ОС, покрывает и COM, и TCP, и BLE почти без нативного кода.
- Единственное ограничение — дистрибуция (`PyInstaller` для Win, PyInstaller +
  Linux-таргет для Linux), решается однократной настройкой сборки.

Альтернативы (если понадобится single-binary без рантайма): **Go + Fyne**
(`go.bug.st/serial`, `tinygo-org/bluetooth`) — компактный бинарник, но дороже по
кодам/токенам и слабее BLE на Windows; **Rust + egui/iced + serialport/btleplug** —
лучшая производительность, самая высокая стоимость разработки.

## 2.1. Статус реализации (факт)

Реализовано в `energybms-editor/energybms_editor/` (Python + PySide6):

- Транспорты: `transports.py` — `SerialTransport`, `TcpTransport`, `BleTransport`
  (плоский пакет, без подпакетов).
- Кодеки: `protocol.py` — `PaceCodec` (ASCII PACE, один на host/RM485) и
  `BleCodec` (бинарный, CRC-16/CCITT).
- Логика: `params.py` (87 параметров + 8 бит-групп, кодирование/декодирование
  169 Б), `telemetry.py` (декодеры `0x42/0x44/0x51/0x4D/0xA4/0x61`),
  `link.py` (`BmsLink`: чтение блоков и запись `0xA1`).
- UI: `main_window.py`, `params_tab.py`, `connect_dialog.py`.
- Конфиг: `config.py` — JSON рядом с запускаемым модулем.

Реализованные чтения: RS485 host — `0x42/0x44/0x4F/0x51/0x47/0x4D/0xA4`;
RM485 — `0x42/0x44/0x4F/0x51`; BLE — `0x51/0x61/0x62/0x47`. Запись — только
`0xA1` (блок параметров). Смена CAN-протокола (`0x63`/`0xA6`), запись времени
(`0x4E`), SN (`0xA3/0xA5`), история (`0x4B`) **не реализованы**.

**Пока не реализовано (план, §5 и §4.2 ниже):** автоопределение канала
(`Detector`), класс `ChannelProfile`, `profiles.py`, кэш профилей по SN.
Сейчас роль порта (host/RM485) и транспорт выбираются вручную в диалоге
соединения; capabilities заданы в кодеках.

## 3. Ключевой вывод анализа архитектуры

> **Логический протокол один.** Это семейство «CID» YD/T 1363 (PACE): общий
> словарь команд `CID1=0x46`/`CID2`, код `RTN`, единая семантика полей и
> параметров. Различия между каналами — это **не разные протоколы**, а разные
> **wire-представление** и **доступность функций** на конкретном порту.

Из этого следуют **три независимые оси**:

| Ось | Что варьируется | Примеры |
|-----|----------------|---------|
| **1. Логика** (единая, общая) | команды, `CID2`, словарь параметров, семантика полей, `RTN` | `0x42` TeleMeter, `0x47` параметры, `0xA1` запись |
| **2. Wire-представление** (кодек) | как логика кодируется в байты кадра | бинарный кадр `7E 14 ADR ... 0D` (BLE) vs ASCII-hex PACE `~VER ADR 46 ...` (RS485) |
| **3. Роль/доступность** (профиль канала) | какие `CID2` доступны, нужен ли `INFO`, baud, можно ли писать | host-RS485 (`LEN=0000`, `0x47` есть) vs RM485 (`INFO=[00]`, `0x47` → `RTN=04`) |

**Важно:** Solarman/Modbus/Enjie-бинарный — это диалекты **диагностики самого
моста** (`tools/tcp_probe.py`), к протоколу BMS не относятся и в приложение
не входят.

### 3.1. Отличия каналов (факты)

| Канал | Кодировка кадра | Контроль | INFO в read | Baud | Параметры (`0x47`) |
|-------|----------------|----------|-------------|------|--------------------|
| BLE (BT2-мост) | бинарный `7E 10/14 ADR CID2 [RTN] LEN INFO CHK 0D` | CRC-16/CCITT | по команде | — | см. `protocol-BLE.md` |
| host-RS485 (п. 10.2) | ASCII-hex PACE `~ VER ADR 46 CID2 LEN INFO CHK CR` | 16-бит. дополнение суммы ASCII | **нет** (`LEN=0000`); при INFO → `RTN=03` | 19200 | ✅ 169 Б, запись `0xA1` |
| RM485 (п. 10.1) | ASCII-hex PACE (то же ядро) | то же | **нужен** `INFO=[00]` (`LEN=0xF001`) для `0x42/0x44` | 9600 | ❌ `RTN=04` |

Отличия доступных функций — это **назначение порта**, а не прошивка
(см. `protocol-485.md` §1.2).

## 4. Архитектура

Три слоя, где UI и логика не знают о конкретном канале:

```
┌──────────────────────────────────────────────────────────────┐
│ UI (PySide6)                                                 │
│   спрашивает PARAM_TABLE (логика) + ChannelProfile (доступно) │
└──────────────────────────────────────────────────────────────┘
                 │ BmsCommand / Frame
┌──────────────────────────────────────────────────────────────┐
│ Codec (wire-представление)                                   │
│   BleBinaryCodec | PaceAsciiCodec                            │
│   encode(BmsCommand) -> bytes ; decode(raw) -> BmsCommand    │
└──────────────────────────────────────────────────────────────┘
                 │ bytes
┌──────────────────────────────────────────────────────────────┐
│ Transport                                                    │
│   SerialTransport | TcpTransparentTransport | BleTransport   │
└──────────────────────────────────────────────────────────────┘
        ▲
        │ выбирается
┌──────────────────────────────────────────────────────────────┐
│ Detector — определяет codec + ChannelProfile для endpoint    │
└──────────────────────────────────────────────────────────────┘
```

### 4.1. Логическая модель (единая)

```python
class BmsCommand:
    cid1: int          # 0x46
    cid2: int          # 0x42, 0x44, 0x47, 0xA1, ...
    info: bytes        # payload запроса
    direction: str     # request | response
    rtn: int | None    # только для ответа

PARAM_TABLE: dict[int, ParamSpec]   # адрес → имя, тип, биты, RW, описание, ед.
```

Словарь параметров (`PARAM_TABLE`) — единственный источник истины для UI,
BER-редакторов и валидации; строится по `protocol-485.md` §8 и
`16S_V20_ADDR_EN.xml`. Телеметрия (`0x42`) и состояние (`0x44`) — read-only.

### 4.2. Интерфейсы слоёв (фактические)

```python
class Transport:                      # transports.py
    kind: str
    def connect(self) -> None: ...
    def query(self, frame: bytes, timeout: float) -> bytes: ...
    def close(self) -> None: ...

class PaceCodec / BleCodec:           # protocol.py
    def capabilities(self) -> list[int]: ...
    def frame_for_read(self, cid2: int) -> bytes: ...
    def frame_for_write(self, cid2: int, payload: bytes = b"") -> bytes: ...
    def parse_many(self, raw: bytes) -> list[dict]: ...  # {cid2,rtn,info,ok}

class BmsLink:                        # link.py
    def connect(self) -> None: ...
    def read_block(self, cid2, wait=None) -> FrameResult: ...
    def read_all(self) -> dict[int, FrameResult]: ...
    def write_params(self, model: dict) -> FrameResult: ...
```

Параметры — `params.PARAMS` (список кортежей) + `PARAM_BY_INDEX`, а не
`dict[int, ParamSpec]`. Интерфейс целиком построен на `cid2`-функциях, без
отдельного класса `BmsCommand`.

### 4.3. Структура каталогов (фактическая)

```
energybms-editor/
  run_editor.py
  requirements.txt
  README.md
  energybms_editor/
    protocol.py       # PaceCodec + BleCodec, CID/RTN
    params.py         # PARAMS + BITGROUPS, encode/decode 169 Б
    telemetry.py      # декодеры 0x42/0x44/0x51/0x4D/0xA4/0x61
    transports.py     # Serial / TCP / BLE (только байты)
    link.py           # BmsLink: чтение блоков, запись 0xA1
    config.py         # JSON рядом с запускаемым модулем
    main_window.py    # окно, вкладки, IoWorker (QThread)
    params_tab.py     # блокировка/редактирование/валидация/подтверждение
    connect_dialog.py # диалог соединения + потоковый BLE-скан
    main.py           # точка входа
```

Ключевое: `PaceCodec` — **один** на host-RS485 и RM485; разницу задаёт
параметр `port_type` (host/RM485), влияющий на `capabilities()` и на наличие
`INFO` в read-командах `0x42/0x44`. Планируемый `ChannelProfile` (§5) должен
заменить эту ручную конфигурацию.

## 5. Автоопределение канала («в какой порт воткнули провод») — ПЛАН

> **Статус:** в текущей реализации отсутствует. Роль порта (host/RM485) и
> транспорт выбираются вручную в диалоге соединения; capabilities заданы в
> кодеках. Ниже — проектируемый слой `Detector` (пока не написан).

У прозрачного TCP-шлюза приложение **не управляет портом и baud** — это физика
шлюза. Поэтому канал определяется **отпечатком** (fingerprint), а не адресом.
Детектор решает только две вещи (не «какой протокол»):

1. **Wire-представление.** Ответ валиден как бинарный кадр (CRC-16/CCITT) →
   BLE-канал. Валиден как ASCII PACE (корректный `CHK`, `CID1=0x46`) →
   RS485-канал.
2. **Роль.** Для PACE шлём безопасную read-команду и смотрим framing:
   - `0x42` с `INFO=[00]` → валидный ответ ⇒ **RM485**;
   - `0x42` без INFO (`LEN=0000`) → валидный ответ ⇒ **host-RS485**
     (при INFO host вернёт `RTN=03` Len Check Error).

Алгоритм:

```
for endpoint in candidates:
    bytes = send(safe_read)          # 0x42
    frame = codec.decode(bytes)
    if codec.is_valid(bytes) and frame.rtn == 0:
        profile = build_profile(codec, role_from_framing)
        break
```

- Валидность = **сумма/CRC + ожидаемый `CID2` + `RTN=00`**, не «пришли байты».
- Победивший профиль кэшируется (планируется: по endpoint и/или SN из `0xA4`)
  и больше не перепробуется.
- Подтверждение устройства: чтение `0xA4` (BatSN, напр.
  `EMU110110S-XXXX-20220120-00001`) — привязка профиля к серийнику,
  различение нескольких BMS за одним шлюзом.
- Ручной override профиля в UI на случай ошибки автодетекта.
- Для **BLE** детект проще: кодек один (`BleCodec`), устройство выбирается по
  имени/адресу; capabilities задаются кодеком.

## 6. UI (PySide6)

- **Вкладка «Телеметрия»** (`0x42`): таблица + realtime-графики (`pyqtgraph`).
- **Вкладка «Состояние/защиты»** (`0x44`): битовая карта предупреждений/защит.
- **Вкладка «Параметры»** (`0x47`): редактируемая таблица по `PARAM_TABLE`,
  подсветка RW, валидация типов/диапазонов, «Сохранить» → `0xA1`.
- **Вкладка «Инфо/SN»** (`0x4F/0x51/0xA4`).
- **Строка подключения**: выбор транспорта (COM / TCP host:port / BLE), кнопка
  «Определить» (детектор), индикатор профиля и `baud`/роли.
- **UX доступности:** недоступные на текущем профиле команды/поля — заблокированы
  (RM485: параметры read-only/недоступны; host: RW).
- **Безопасность записи:** явное подтверждение перед `0xA1`, логирование
  «было → стало», запрет записи без выбранного профиля.

## 7. Протокольные факты, используемые в коде

### 7.1. Кадры

```
Бинарный (BLE):
  Запрос: 7E 10 ADR 46 CID2 LEN(2) INFO CHKSUM(2) 0D
  Ответ:  7E 14 ADR CID2 RTN LEN(2) INFO CHKSUM(2) 0D
  Полная длина = 10 + LENID ; CRC-16/CCITT.

ASCII PACE (RS485):
  Запрос: ~ VER(2) ADR(2) 46 CID2(2) LEN(4) INFO(hex) CHK(4) CR
  Ответ:  ~ VER(2) ADR(2) 46 RTN(2) LEN(4) INFO(hex) CHK(4) CR
  ~ = 0x7E, CR = 0x0D, все поля ASCII-hex.
  LENID = len(INFO) в байтах (запрос) / число hex-символов INFO (ответ).
  LCHKSUM = 4-бит. дополнение суммы нибблов LENID.
  CHK = ((~sum(ord(c))) & 0xFFFF) + 1 по символам VER..INFO.
```

### 7.2. Доступность команд `CID2`

| CID2 | Имя | RM485 (9600) | host-RS485 (19200) |
|------|-----|--------------|--------------------|
| `0x42` | TeleMeter | ✅ 75 Б (`INFO=[00]`) | ✅ 75 Б (без INFO) |
| `0x44` | TeleState | ✅ 49 Б (`INFO=[00]`) | ✅ 49 Б (без INFO) |
| `0x4F` | ProtocolVer | ✅ | ✅ |
| `0x51` | Manufacture | ✅ 32 Б | ✅ 32 Б |
| `0x47` | GetAllParas | ❌ `RTN=04` | ✅ 169 Б |
| `0x4B` | GetHistoryData | ❌ | ✅ 97 Б |
| `0x4D` | GetTime | ❌ | ✅ 7 Б |
| `0xA4` | GetBatSN | ❌ | ✅ 30 Б ASCII |
| `0x49` | SetPara (один) | — | ❌ `RTN=04` |
| `0xA1` | SetAllParas | — | ✅ 169 Б |
| `0x4E` | SetTime | — | ✅ 7 Б |

`CID1 = 0x46`, `SOI = 0x7E`, `EOI = 0x0D`. Коды `RTN`: `00` Normal …
`04` No Support, `03` Len Check Error и др. (см. `protocol-485.md` §3).

> **Реализовано в приложении:** чтения `0x42/0x44/0x4F/0x51/0x47/0x4D/0xA4`
> (RS485 host), `0x42/0x44/0x4F/0x51` (RM485), `0x51/0x61/0x62/0x47` (BLE);
> запись `0xA1`. Строки `0x4B`, `0x49`, `0x4E` приведены для полноты и в
> текущей версии **не используются**.

### 7.3. Транспорт BLE

Сервис `0000ff00`, запись `0000ff02` (handle `0x14`), уведомления `0000ff01`
(handle `0x11`). BMS `BP00` `28:xx:xx:xx:xx:xx`.

## 8. Что НЕ входит в архитектуру

- **Modbus / Solarman / Enjie-бинарный (`tcp_probe.py`)** — это распознавание
  диалекта самого моста (диагностика), к логике BMS не относится.
- Управление параметрами шлюза (baud, режим, пароли, ребут) — по правилам
  проекта операции со шлюзом `192.0.2.77` ограничены; приложение только
  использует прозрачный канал.
- Запись в BMS без явного разрешения пользователя. Напоминание: `AGENTS.md`
  устанавливает «в BMS ничего не писать, только чтение»; команда `0xA1`
  реализована по запросу на разработку редактора и должна запускаться против
  живого устройства только по отдельному явному разрешению.

## 9. Открытые вопросы и план

Сделано: `Transport`/кодеки/`BmsLink`, `PARAMS`+`BITGROUPS`, UI (вкладки,
блокировка/редактирование/валидация/подтверждение), запись `0xA1`.
Реализация — `energybms-editor/`.

Осталось:
1. Автоопределение канала: `Detector` + `ChannelProfile` (роль host/RM по
   framing `0x42`) вместо ручного выбора.
2. Кэш профилей (endpoint/SN) — вне `.kilo/` или в нём, с учётом портативности.
3. Графики телеметрии (`pyqtgraph`), если понадобятся.
4. Сборка дистрибутивов: PyInstaller (Win64) и Linux64.
5. Опционально: смена CAN-протокола (`0x63`/`0xA6`), запись времени `0x4E`,
   история `0x4B` — по отдельному разрешению.
