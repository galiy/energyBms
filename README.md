# EnergyBMS

Реверс-инжиниринг протокола обмена BMS-устройства **EMU1101** (8S–16S LFP/NCM,
100–300 A) производства **Shanghai Enjie Electronic Technology Co., Ltd.**
(бренд **N ENERGY** / **EN**, 上海恩阶电子科技有限公司).

Устройство общается с инвертором по CAN/RS-485, а с приложением — по Bluetooth
Low Energy. Цель проекта — полностью восстановить «верхний» протокол платы
(тот же кадр, что идёт по RS-485 и через BLE-мост BT2), чтобы уметь читать
телеметрию и писать параметры/режимы без фирменного ПО.

## Статус

**Протокол восстановлен и подтверждён двумя независимыми источниками:**
читаются телеметрия, защиты и блок из 169 байт параметров; восстановлены
форматы чтения и **записи** параметров, флагов, режимов, времени, SN и
расписания. Идентифицировано семейство (YD/T 1363 / Pylontech / PACE «CID»).

## Кратко о протоколе

```
Запрос:  7E | 10 | ADR | 46 | CID2 | LEN(2) | INFO | CHKSUM(2) | 0D
Ответ:   7E | 14 | ADR | CID2 | RTN | LEN(2) | INFO | CHKSUM(2) | 0D
```

- Полная длина кадра = `10 + LENID`; в ответе `LENID = frame[5]<<8 | frame[6]`,
  `INFO` — с байта 7 (уточнено живым захватом 2026-09-30; ранее в описаниях
  ответа байт `RTN` был пропущен).

- Транспорт BLE: сервис `0000ff00`, запись `0000ff02` (h `0x14`), уведомления `0000ff01` (h `0x11`).
- RS-485: host-RS485 baud **19200**, RM485 — **9600**; на RS485 диалект ASCII PACE
  (см. `protocol-485.md`), а не бинарный кадр BLE.
- `CID1 = 0x46`, `SOI = 0x7E`, `EOI = 0x0D`; ключевые команды: `0x42` телеметрия,
  `0x44` защиты, `0x47`/`0xA1` чтение/запись параметров, `0x45` управление,
  `0x49` запись одного параметра/флага. Выбор CAN-протокола: **`0x63`** на BLE
  (диалект приложения) и **`0xA6`** на RS485 (диалект Upper Computer).
- Контроль: BLE/приложение — CRC-16/CCITT; RS485/Upper Computer — 16-битная
  сумма-дополнение ASCII (см. `protocol-BLE.md` §3.3, `protocol-485.md` §2).

Подробно — в [`protocol-BLE.md`](protocol-BLE.md).

## Транспорт и железо (находки 2026-10-02)

- **BLE-опрос стабильнее через отдельный хост** `gsrv` (`user@192.0.2.253`):
  BMS `BP00` (`28:xx:xx:xx:xx:xx`, сервис `ff00`, notify `ff01` / write `ff02`).
  Пароль хоста — в связке ключей (`secret-tool lookup server 192.0.2.253`).
- **TCP-мост** `USR-DR164` (PUSR): `192.0.2.75`, веб `<login>/<password>` (в `.kilo/`), TCP Server
  :8899, прозрачный режим (**ModBUS Enabled = OFF**), serial 9600/19200 8N1.
- **RS485 РАБОТАЕТ** (проверено 2026-10-04 через прозрачный IP-RS485-шлюз
  `192.0.2.77:502`): диалект — **ASCII-hex PACE** (не бинарный, не Modbus).
  Два порта: **RM485** (п. 10.1, 9600) — телеметрия/состояние, параметры
  недоступны; **host-RS485** (п. 10.2, 19200) — помимо телеметрии/состояния
  отдаёт **параметры** (`0x47`, 169 Б), время (`0x4D`), историю (`0x4B`) и SN
  (`0xA4`). Важно: на host-порту read-команды идут **без INFO** (`LEN=0000`).
  Канал инвертора — **CAN** (команда `0x64` «switch 485» относится к
  инверторному CAN/RM485 и даёт `RTN=0xE2`). Подробности — `protocol-485.md`.
- **Переключение инверторного CAN-протокола** — команда `0x63`, payload = тип
  `1..7` (`1`=PN-GDLT … `7`=MUST); проверено на живом устройстве. Детали и коды
  `RTN` — в `protocol-BLE.md` §13.

## Бэклог

- Подтвердить смысл байтов `Ext_Bit[14..18]` TeleState на живом изменении режима
  (структура/длина уже точны — см. `protocol-485.md` §6).
- Разобрать формат истории (`0x4B`, 97 Б на запись) и даты/времени.
- Проверить адресацию слейвов (`ADR=01..0F`) при параллельной сборке.
- Сверить параметры RS485 с BLE-эталоном (`DEVICE_SNAPSHOT.md` §4).
- Задокументировать запись параметров (`0xA1`/`0x49`) по отдельному разрешению.
- Реализовать RS485-транспорт (host-RS485, PACE) в проекте sunReceiver (модуль
  `enBms`) — сейчас опрос BMS там только по BLE.
